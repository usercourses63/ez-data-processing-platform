# System Monitoring Component

Real-time system monitoring dashboard with SignalR WebSocket integration, providing live visibility into service health, Kafka queues, distributed traces, pipeline events, and device health.

## Features

- **Real-Time Updates**: SignalR WebSocket connection for live data streaming
- **Dual-Speed Broadcast**: 5-second interval for fast-changing data (services, Kafka), 30-second for slow data (traces, events)
- **Connection Recovery**: Automatic reconnection with configurable retry intervals
- **Fallback Polling**: React Query polling when SignalR is unavailable
- **Multi-Tab Dashboard**: Overview, Device Health, Pods, Traces, Queues, Alerts
- **Connection Status Indicator**: Visual dot showing connected/disconnected/reconnecting state

## SignalR Integration

### Connection Lifecycle

The `useMonitoringHub` hook manages the full SignalR connection lifecycle:

1. **Initial Connection**: Connects to `/hubs/monitoring` on mount
2. **InitialState**: Receives full state snapshot on first connect
3. **Live Updates**: Receives incremental updates for each data type
4. **Reconnection**: Automatic retry with backoff: `[0, 2000, 5000, 10000, 30000]` ms
5. **Cleanup**: Graceful disconnection on component unmount

```typescript
import { useMonitoringHub } from '../../hooks/useMonitoringHub';

const hubUrl = `${window.location.protocol}//${window.location.host}/hubs/monitoring`;
const {
  connectionState, isConnected,
  deviceHealth, services, pods, metrics,
  queues, alerts, trace, clusterInfo,
  events, lastUpdate
} = useMonitoringHub(hubUrl);
```

### Dual-Speed Broadcast

The backend `MonitoringBroadcaster` hosted service uses two broadcast intervals:

| Speed | Interval | Data Types |
|-------|----------|------------|
| Fast  | 5 seconds | Services, Kafka queues, Pods, Metrics |
| Slow  | 30 seconds | Traces, Events, Alerts, Device Health |

### Connection Recovery

- Automatic reconnection with exponential backoff
- Toast notifications for connection lost/restored
- `isMountedRef` guard prevents state updates after unmount
- `wasConnectedRef` tracks whether initial connection succeeded (prevents false "reconnected" toasts)

### PascalCase Mapper Functions

Backend sends PascalCase JSON (due to `PropertyNamingPolicy = null`). The hook includes mapper functions for each data type:

```typescript
// Example: mapServiceStatus converts backend PascalCase to frontend camelCase
function mapServiceStatus(raw: any): ServiceStatus {
  return {
    id: raw.Id,
    name: raw.Name,
    status: raw.Status?.toLowerCase?.() ?? 'unknown',
    // ... etc
  };
}
```

Mapper functions exist for: `ServiceStatus`, `PodStatus`, `DashboardMetrics`, `MessageQueue`, `Alert`, `DistributedTrace`, `ClusterInfo`, `PipelineEvent`.

The `ClusterHeader` component displays a connection status indicator:

| State | Visual | Description |
|-------|--------|-------------|
| Connected | Green dot | Live SignalR data streaming |
| Reconnecting | Yellow dot | Connection lost, attempting recovery |
| Disconnected | Red dot | No SignalR connection, using polling fallback |

## Fallback Behavior

When SignalR is unavailable, the dashboard falls back to:

1. **Mock data**: Generated locally for initial display
2. **Polling interval**: 30-second refresh cycle for mock data
3. **React Query polling**: 15-second interval for Device Health API (independent of SignalR)

```typescript
// Only run mock refresh when SignalR is NOT connected
useEffect(() => {
  loadDashboardData();
  if (!isConnected) {
    const interval = setInterval(loadDashboardData, 30000);
    return () => clearInterval(interval);
  }
}, [isConnected]);
```

## v0.3.0 Changes

### RabbitMQ Queue Monitoring

The Queues tab now monitors RabbitMQ queues instead of Kafka topics for internal service communication. Kafka monitoring remains for external data source connectors only. Queue status shows message count, consumer count, and queue state.

### Pipeline Flow with K8s Deployment IDs

The PipelineFlow component now uses actual Kubernetes deployment identifiers for flow lane rendering. Each lane corresponds to a real deployment (e.g., `filediscovery`, `fileprocessor`, `validation`, `output`) rather than static mock labels.

### Traces Tab Improvements

The Traces tab now queries all pipeline services with relative timing display:

- **Service Coverage**: Queries traces across FileDiscovery, FileProcessor, Validation, Output, and Scheduling services
- **Relative Timing**: Span start times shown relative to the trace root (e.g., "+45ms" instead of absolute timestamps)
- **Shortened Service Names**: The `DataProcessing.` prefix is stripped from service names for cleaner display (e.g., "FileProcessor" instead of "DataProcessing.FileProcessor")

### Dual-Casing SignalR Mappers

All SignalR mapper functions now handle both camelCase and PascalCase property names. This prevents crashes when the backend serialization format changes or when different services use different naming policies:

```typescript
// v0.3.0: All mappers handle dual casing
function mapServiceStatus(raw: any): ServiceStatus {
  return {
    id: raw.Id ?? raw.id,
    name: raw.Name ?? raw.name,
    status: (raw.Status ?? raw.status)?.toLowerCase?.() ?? 'unknown',
    cpu: raw.Cpu ?? raw.cpu ?? 0,
    memory: raw.Memory ?? raw.memory ?? 0,
    // ... all properties handle both casings
  };
}
```

Affected mappers: `ServiceStatus`, `PodStatus`, `DashboardMetrics`, `MessageQueue`, `Alert`, `DistributedTrace`, `ClusterInfo`, `PipelineEvent`, `DeviceHealthStatusResponse`.
