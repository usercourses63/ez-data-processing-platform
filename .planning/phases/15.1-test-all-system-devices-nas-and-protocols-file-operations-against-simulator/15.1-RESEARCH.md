# Phase 15.1: Test All System Devices (NAS and Protocols) File Operations Against Simulator - Research

**Researched:** 2026-02-26
**Domain:** Playwright E2E testing, file protocol connectors, file-simulator REST API, cross-cluster Hyper-V networking

## Summary

This phase is a pure testing/validation phase. All 8 connector implementations already exist in `src/Services/Shared/Connectors/` and implement the `IServerConnector` interface with `TestConnectionAsync`, `ListFilesAsync`, `ReadFileAsync`, and `WriteFileAsync` operations. The file-simulator cluster provides FTP, SFTP, NAS/NFS, HTTP/WebDAV, S3, and Kafka endpoints, and supports dynamic server creation via REST API (`POST /api/servers/{protocol}`).

The test suite will use Playwright E2E tests in `src/Frontend/tests/e2e/`. Two scenarios are required: Scenario A tests file operations against pre-existing static simulator devices; Scenario B creates dynamic servers via the simulator API, registers them in EZ through the System Settings UI (Playwright), then runs the same file operation matrix. File operations are exercised through the backend REST API via Playwright's `request` context (not through the UI), while device creation/registration happens through the UI.

**Primary recommendation:** Structure as one test file per protocol, with shared fixtures for test data files (CSV, JSON, XML, Excel) and a shared helper module for simulator API interaction, EZ API interaction, and the protocol x format result matrix reporter.

### Pattern 1: Two-Phase Test Execution (Static then Dynamic)
**What:** Each protocol test file runs two describe blocks - Scenario A (static devices) and Scenario B (dynamic devices)
**When to use:** Every protocol test file
**Example:**
```typescript
test.describe('FTP - Scenario A: Static Devices', () => {
  // Use pre-existing simulator FTP servers
  // Discover via GET /api/servers → filter protocol=ftp
  // Run file operation matrix
});

test.describe('FTP - Scenario B: Dynamic Devices', () => {
  // 1. Create FTP server via simulator API (POST /api/servers/ftp)
  // 2. Register in EZ via System Settings UI (Playwright)
  // 3. Run same file operation matrix
  // 4. Cleanup in afterAll
});
```

### Pattern 2: File Operations via Backend API (request context)
**What:** File operations (read, write, list) are tested by calling the EZ backend APIs directly using Playwright's `request` fixture, NOT through the UI
**When to use:** All file operation testing
**Example:**

### Anti-Patterns to Avoid
- **Testing file operations through the UI:** The UI does not expose read/write/list. Use `request` context to call backend APIs directly.
- **Hardcoding simulator IPs:** Use environment variables (FILE_SIMULATOR_URL) since IPs may change.
- **Using port-forward for tests:** Port-forward hangs with Hyper-V driver. Use NodePort + direct minikube IP (172.17.89.141 for file-simulator).
- **Skipping tests when simulator unavailable:** Per project convention, tests MUST fail (not skip) if file-simulator is unreachable.
- **Creating test data dynamically in tests:** Test data files are pre-created in repo as static fixtures.

## Protocol Capability Matrix

### Per-Protocol Operations
Based on the actual connector implementations in the codebase:

| Protocol | ConnectorType | List | Read | Write | TestConnection | Notes |
|----------|---------------|------|------|-------|----------------|-------|
| FTP | `ftp` | YES | YES | YES | YES | FluentFTP; passive mode default |
| SFTP | `sftp` | YES | YES | YES | YES | SSH.NET; password + key auth |
| HTTP/WebDAV | `http` | YES (via list endpoint) | YES (GET) | YES (PUT) | YES (GET health) | HTTP write = PUT to URL |
| S3 | `s3` | YES | YES | YES | YES | AWS SDK; MinIO/S3-compat via endpoint |
| Kafka (local) | `kafka` | YES (consume N) | YES (consume at offset) | N/A | YES (admin client) | No write - Kafka is consume-only in IDataSourceConnector |
| Kafka (simulator) | `kafka` | YES | YES | N/A | YES | Same connector, different bootstrap server |
| NAS/NFS | `nfs` | YES | YES | YES | YES | PVC mount path; filesystem operations |
| SMB | `smb` | YES | YES | YES | YES | SMBLibrary; port 445 required |

**Key observation on Kafka:** The `KafkaConnector` only implements `IDataSourceConnector`, NOT `IServerConnector`. It lacks `WriteFileAsync`. Kafka tests should cover List + Read + TestConnection only (no Write). This is protocol-appropriate since Kafka in EZ is used for consuming file data, not producing.

**Key observation on HTTP:** The `HttpApiConnector` implements both interfaces. Write uses HTTP PUT. List requires a dedicated list endpoint to return JSON array of paths.

**Key observation on NFS/NAS:** NFS operations go through the filesystem (PVC mount). The test needs the NAS device to be provisioned (PV/PVC created and mounted to pods) for file operations to work.

### File Format Coverage Per Protocol

Not all protocols handle all formats identically. The operation is format-agnostic at the connector level (bytes in, bytes out), but the test should verify that each format's content survives the round-trip correctly:

| Format | Extension | Content-Type | Binary? | Verification Strategy |
|--------|-----------|-------------|---------|----------------------|
| CSV | .csv | text/csv | No | Text comparison |
| JSON | .json | application/json | No | JSON parse + deep compare |
| XML | .xml | application/xml | No | Text comparison |
| Excel | .xlsx | application/vnd.openxmlformats... | Yes | Byte-level size comparison (binary) |

### Connection Testing (Protocol-Specific)
```
POST /api/v1/test-connection/kafka  { BrokerServer, Topic }
POST /api/v1/test-connection/folder { Path }
POST /api/v1/test-connection/sftp   { Host, Port, Username, Password }
```

**Important limitation:** The current backend API does NOT expose generic file List/Read/Write endpoints for arbitrary servers. Connection testing is available, and the connectors exist in the backend code, but there is no REST endpoint like `POST /api/v1/servers/{id}/list-files` or `POST /api/v1/servers/{id}/read-file`.

**Recommendation:** For file operation testing, the approach must be:
1. **Connection Test** - Available via existing APIs for all protocols
2. **Write files** - Upload test data files TO the simulator using the file-simulator's own mechanisms (e.g., FTP client upload, S3 put, HTTP PUT) or simulator API if available, rather than through EZ APIs
3. **List/Read verification** - Can be validated indirectly through the EZ pipeline (DataSource file discovery) or by calling backend APIs if endpoints exist

**Alternative approach:** Since the connectors work at the service level, not the API level, the most practical testing strategy may be:
- Use the **file-simulator direct endpoints** to seed test files into each protocol server
- Use **EZ's connection test APIs** to verify connectivity per server
- Use the **file-simulator's file listing/download APIs** to verify files after write operations
- For full connector testing, consider adding a lightweight REST endpoint in DataSourceManagement that proxies to the connectors

## Common Pitfalls

### Pitfall 1: Port-Forward Hangs with Hyper-V
**What goes wrong:** `kubectl port-forward` hangs indefinitely with Hyper-V driver
**Why it happens:** Known Hyper-V driver issue documented in MEMORY.md
**How to avoid:** Always use NodePort + direct minikube IP. File-simulator at `172.17.89.141:30500` (management), EZ frontend at minikube-IP:30080
**Warning signs:** Test hangs at network call, no timeout error

### Pitfall 2: PascalCase vs camelCase API Payloads
**What goes wrong:** Frontend sends camelCase, backend expects PascalCase (PropertyNamingPolicy = null)
**Why it happens:** Backend uses `PropertyNamingPolicy = null` meaning PascalCase
**How to avoid:** All API request bodies from Playwright must use PascalCase: `Name`, `Host`, `Port`, `ServerType`, `Direction`, etc.
**Warning signs:** 400 Bad Request with model validation errors, fields showing as null/default

### Pitfall 3: Ant Design RTL Tab Click Issue
**What goes wrong:** Playwright `.click()` on Ant Design tab elements does NOT trigger React state change
**Why it happens:** Known RTL/Ant Design interaction issue
**How to avoid:** Use `page.evaluate(() => el.dispatchEvent(new MouseEvent('click', {bubbles:true})))` instead
**Warning signs:** Tab appears clicked but content doesn't change

### Pitfall 4: NAS Role Numeric Enum
**What goes wrong:** Backend returns NAS Role as numeric (0=Input, 1=Output, 2=Backup, 3=Both), frontend type declares string union
**Why it happens:** BsonRepresentation(BsonType.String) serializes as string in MongoDB but API may return numeric
**How to avoid:** Use `roleEnumToString` mapping. When creating NAS devices via API, send string values ("Input", "Output", "Both")
**Warning signs:** NAS device dropdown appears empty, role-based filtering returns no results

### Pitfall 5: SMB Requires Port 445 (Not Configurable)
**What goes wrong:** SMBLibrary DirectTCPTransport always uses port 445, ignoring custom port settings
**Why it happens:** SMB protocol specification; NodePort mapping doesn't work for SMB
**How to avoid:** Use `minikube tunnel` for SMB testing against file-simulator, or accept SMB testing limitation
**Warning signs:** Connection refused to any port other than 445

### Pitfall 6: Kafka Has No Write Operation
**What goes wrong:** Attempting to test "write" on Kafka fails - no WriteFileAsync method
**Why it happens:** KafkaConnector implements only IDataSourceConnector, not IServerConnector
**How to avoid:** Skip write operation for Kafka; test only List + Read + TestConnection
**Warning signs:** Method not found / interface cast failure

### Pitfall 7: NFS Requires Provisioned PV/PVC
**What goes wrong:** NFS connector cannot read/write/list files because mount path doesn't exist
**Why it happens:** NFS operates on PVC-mounted filesystem paths; without provisioning, the path `/mnt/{nas-device-name}` doesn't exist in the pod
**How to avoid:** Must provision NAS device (create PV/PVC and restart pods for volume mount) BEFORE running file operations
**Warning signs:** "NFS: Mount directory does not exist" error

### Pitfall 8: Ant Design Select Drops Values Before Options Load
**What goes wrong:** `form.setFieldsValue()` silently discards values for Select components whose options haven't loaded yet (useQuery async)
**Why it happens:** Ant Design Select discards values that don't match any loaded option
**How to avoid:** Wait for options to load (waitForResponse or waitForSelector on .ant-select-item-option) before asserting selection
**Warning signs:** Dropdown shows "Select..." placeholder instead of expected value

## Open Questions

1. **File-simulator file management API**
   - What we know: The simulator has `/api/servers` for discovery and `/api/servers/{type}` for creation. FileSimulatorClient.cs shows health, servers, connection-info, and create endpoints.
   - What's unclear: Does the file-simulator have a REST API for uploading/downloading files to/from its servers? (e.g., `POST /api/servers/{name}/files`). Without this, seeding test files into protocol servers requires direct protocol access from the test environment.
   - Recommendation: Check the file-simulator API at runtime. If no file upload endpoint exists, use Playwright's request context to upload files directly via each protocol (using the file-simulator's exposed NodePorts).

2. **SMB Port 445 accessibility across Hyper-V clusters**
   - What we know: SMBLibrary always uses port 445 (not configurable). NodePort mapping doesn't work for SMB.
   - What's unclear: Can minikube tunnel expose port 445 across Hyper-V clusters reliably?
   - Recommendation: Include SMB in the test matrix but mark it as "may fail due to port 445 constraint". If it fails, document the limitation rather than blocking the phase.

3. **Backend file operation REST endpoints**
   - What we know: Connection test endpoints exist for servers and NAS devices. Connectors have full List/Read/Write capabilities in code.
   - What's unclear: Are there REST endpoints that expose connector List/Read/Write operations? The controllers only show CRUD + test-connection, not file operations.
   - Recommendation: If no file operation endpoints exist, the planner should include a task to add lightweight proxy endpoints (e.g., `POST /api/v1/servers/{id}/list-files`, `POST /api/v1/servers/{id}/read-file`, `POST /api/v1/servers/{id}/write-file`) in DataSourceManagementService. These would proxy to the IServerConnector methods.
