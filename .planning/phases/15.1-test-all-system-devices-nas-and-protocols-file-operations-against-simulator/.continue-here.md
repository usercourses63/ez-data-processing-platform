#### NEW BUG FOUND: Deployment Rollout Race Condition
- **Root cause:** When `ProvisionNasDeviceAsync` runs, it calls `AutoMountToDeploymentsAsync` which patches the datasource-management deployment with new volume+volumeMount. This triggers a Kubernetes pod rollout.
- **Problem:** The test immediately tries file operations (Write) but the request hits the OLD pod (still running, without the new mount) → "Access to the path '/mnt/...' is denied."
- **The NEW pod with the NFS mount is still starting (ContainerCreating → Running → Ready)**
- **This is NOT a permissions issue — it's a timing issue.** The old pod doesn't have the mount path at all.
- TestConnection passes because it talks to the NFS server directly (no local mount needed)
- Write/List/Read fail because they use LocalFileConnector which reads from the pod's filesystem

#### FIX NEEDED (2 changes):
1. **In `ez-api-client.ts`:** Add `waitForDeploymentReady()` function that polls the EZ API health endpoint until the pod with the new mount is ready. After `provisionNasDevice()`, wait for the deployment rollout to complete.
   - Option A: Poll `/health` after provisioning, wait for the pod to restart (simplest)
   - Option B: Add a `/api/v1/nasdevices/{id}/mount-status` endpoint that checks if the mount path exists in the filesystem
   - **Recommended: Option A** — after provision returns, sleep 5s, then poll health every 5s for up to 60s until it returns 200 (new pod ready)

2. **In `nas-nfs.spec.ts` cleanup:** Call deprovision API before deleting NAS device to remove volume mounts from deployment. Currently `deleteNasDevice` may not cascade to deprovision.
   - Add `deprovisionNasDevice()` to ez-api-client.ts
   - Call it in afterAll before delete
