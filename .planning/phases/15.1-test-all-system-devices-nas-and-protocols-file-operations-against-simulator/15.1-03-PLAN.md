    Create the NAS/NFS protocol test file. NAS/NFS is the most complex protocol to test because it requires Kubernetes PV/PVC provisioning before file operations can work on the pod-mounted filesystem paths.

    **NAS/NFS test structure:**

    **Scenario A: Static NAS Devices**
    - `beforeAll`:
      1. Check simulator health (MUST fail if unavailable)
      2. Discover static NAS servers via `getSimulatorServers` (filter `protocol === 'nas'` or `protocol === 'nfs'`)
      3. Get connection info for NFS NodePort/export details
      4. Check if there are already NAS devices registered in EZ (`getNasDevices`) that correspond to the static simulator NAS
      5. If not registered, create NAS device in EZ via API: `createNasDevice(request, { Name: 'E2E-NAS-Static', Host: '172.17.89.141', ExportPath: '/exports/nas-static', Role: 'Both' })`
      6. CRITICAL: Provision the NAS device (`provisionNasDevice`) to create PV/PVC and mount to pods. Wait for provisioning to complete (can take 30-60s for PVC binding and pod restart).
      7. Verify NAS device shows as provisioned before proceeding
    - `test('TestConnection - static NAS')`: Test connection via `testNasConnection`. Report to matrixReporter.
    - For each format in FORMATS:
      - Write: Use the NAS mount path for file operations. NFS connector writes to the PVC-mounted filesystem path (e.g., `/mnt/{nas-device-name}/test-data-{timestamp}.{ext}`). Use `writeFile` through the file operations API. NOTE: The NFS "server" in EZ is the NAS device, not an AdminServer. Check how NFS file operations are exposed -- if via AdminServer with type 'nfs', create one. If NFS uses a different path (NAS device directly), adapt accordingly.
      - List: `listFiles` to verify file appears
      - Read: `readFile` to verify content matches
    - `afterAll`: Clean up test files (best-effort). Do NOT deprovision the NAS device (other tests may use it).

    **Scenario B: Dynamic NAS Devices**
    - `beforeAll`:
      1. Create dynamic NAS server on simulator: `createDynamicNas(request, 'e2e-dynamic-nas-' + Date.now(), '/data/dynamic')`
      2. Wait for NAS server to be ready on simulator
      3. Register NAS device in EZ via UI: `addNasDeviceViaUI(page, { name: 'E2E-NAS-Dynamic-{timestamp}', host: '172.17.89.141', exportPath: '/exports/{dynamic-nas-name}', role: 'Both' })`
      4. Provision via UI or API: `provisionNasViaUI(page, deviceName)` or `provisionNasDevice(request, deviceId)`. API is more reliable.
      5. Wait for provisioning (PVC binding + pod mount can take up to 60s)
      6. Get NAS device ID from API for file operations
    - Run same file operation matrix as Scenario A
    - `afterAll`:
      1. Delete NAS device from EZ (triggers deprovision cascade)
      2. Delete dynamic NAS from simulator (best-effort)

    **NAS/NFS-specific considerations:**
    - NFS operations go through the filesystem, NOT through a network connector. The NfsConnector reads from the PVC mount path inside the pod.
    - The FileOperationsController needs to handle NFS differently: NFS "server" might not be an AdminServer -- it's a NasDevice. Check if there's a way to route file operations through the NAS device ID.
    - ALTERNATIVE: If FileOperationsController only works with AdminServer IDs, and NFS doesn't have an AdminServer, the test may need to:
      a) Create an AdminServer of type 'nfs' that points to the NAS mount path, OR
      b) Use the NAS device's mount path directly through a folder-type connection test, OR
      c) Verify NFS operations indirectly by checking the PVC mount path contents
    - The practical approach: Create an AdminServer with `ServerType: 'folder'` and `BasePath: '/mnt/{nas-device-name}'`. The LocalFileConnector (folder type) can then list/read/write from the NFS-mounted path inside the pod.
    - **Recommended approach**: Check if there's a 'nfs' ServerType in IConnectorFactory. If NfsConnector exists as a standalone connector that works with AdminServer, use it. If not, the folder connector on the NFS mount path is the pragmatic solution.

    **Provisioning wait strategy:**
    After calling `provisionNasDevice`, poll the NAS device status every 5 seconds up to 90 seconds:
    ```typescript
    for (let i = 0; i < 18; i++) {
      const device = await getNasDeviceById(request, deviceId);
      if (device.ProvisioningStatus === 'Bound' || device.MountStatus === 'Mounted') break;
      await new Promise(r => setTimeout(r, 5000));
    }
    ```

    **IMPORTANT:**
    - NFS REQUIRES provisioned PV/PVC. Without provisioning, the mount directory doesn't exist in the pod. (Pitfall 7 from RESEARCH.md)
    - Provisioning triggers pod restarts for volume mounts. Allow time for pods to restart.
    - Test timeout should be higher: `test.setTimeout(120000)` (2 min) for NAS tests that include provisioning wait.
    - Use `matrixReporter.addResult()` for all operations
    - PascalCase for EZ API payloads
