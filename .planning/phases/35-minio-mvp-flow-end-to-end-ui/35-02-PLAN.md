<objective>
Close **G5** — THE primary MVP blocker: the data-source create flow does not persist the S3 output
destination `S3Config` (bucket comes out `null` in Mongo so the output write to MinIO fails / had to
be hand-populated). Make a UI-created S3 output destination persist a complete, write-ready
`Output.Destinations[].S3Config` in Mongo. This is the highest-risk vertical slice and gates SC-5
(run produces a MinIO output object), so it ships in Wave 1.

Root cause (mapped live): `DestinationEditorModal.handleSubmit` S3 branch only sets
`folderConfig.path` and the TS `OutputDestination` type has **no** `s3Config` field; the backend
stores `entity.Output = request.Output` verbatim but the output destination's selected
`OutputServerId` (the AdminServer holding the S3 bucket/endpoint/creds) is **never bridged** into
`S3Config` (only the INPUT `FileServerId` is bridged, in `PopulateFileServerConnectionAsync`). The
`S3OutputHandler.WriteAsync` throws "S3Config is required" when it is null.

Purpose: SC-3 (output server config persists + write succeeds), SC-4 (output S3Config persists on the
data source), SC-5 (enables the run-and-verify slice).
Output: TS `s3Config` field, frontend S3 destination builder, backend output-S3 bridge, unit tests.
</objective>
