# Frontend/Backend API Coordination

Process for coordinating API changes between frontend and backend teams.

## Overview

EZ Platform uses a contract-first approach where API contracts are defined
before implementation to ensure frontend and backend remain synchronized.

## API Contract Location

- **Backend Controllers:** `src/Services/*/Controllers/`
- **API Response Types:** `src/Services/Shared/Models/`
- **Frontend API Clients:** `src/Frontend/src/services/*-api-client.ts`
- **Frontend Types:** `src/Frontend/src/types/`

## Change Process

### 1. Contract Proposal

When changing an API endpoint:

1. **Document the change** in a GitHub issue or PR description
2. **Specify** the endpoint, method, request/response format
3. **Include** breaking vs non-breaking classification

Example format:
```
Endpoint: POST /api/v1/datasources
Change: Add optional `archiveSettings` field to request body
Type: Non-breaking (new optional field)
Request: { ...existing, archiveSettings?: { enabled: boolean, ... } }
```

### 2. Version Strategy

EZ Platform uses URL versioning: `/api/v1/...`

- **Non-breaking changes:** Add to current version
- **Breaking changes:** New version (v2) with deprecation period
- **Deprecation period:** 2 releases minimum

### 3. Implementation Order

For **non-breaking** changes:
1. Backend adds new field/endpoint (backward compatible)
2. Frontend updates to use new field
3. Both can deploy independently

For **breaking** changes:
1. Backend adds new version (v2) alongside old
2. Frontend migrates to v2
3. Old version removed after deprecation period

### 4. Communication Channels

- **GitHub Issues:** API change proposals
- **PR Reviews:** Cross-team review requirement
- **CHANGELOG.md:** Document API changes per release

## API Client Patterns

### TypeScript API Client
```typescript
// src/Frontend/src/services/datasources-api-client.ts
export const dataSourcesApi = {
  async getAll(): Promise<ApiResponse<DataSource[]>> {
    const response = await fetch(`${API_BASE}/api/v1/datasources`);
    return response.json();
  },

  async create(data: CreateDataSourceRequest): Promise<ApiResponse<DataSource>> {
    const response = await fetch(`${API_BASE}/api/v1/datasources`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(data),
    });
    return response.json();
  },
};
```

### Response Wrapper
```typescript
interface ApiResponse<T> {
  data: T;
  isSuccess: boolean;
  message?: string;
  errors?: string[];
}
```

## Checklist for API Changes

- [ ] Change documented in issue/PR
- [ ] Breaking/non-breaking classified
- [ ] Backend controller updated
- [ ] Response type updated in Shared/Models
- [ ] Frontend API client updated
- [ ] Frontend types updated
- [ ] E2E tests updated if behavior changed
- [ ] CHANGELOG entry added

## Common Pitfalls

1. **Undocumented changes:** Always document before implementing
2. **Missing type updates:** Keep frontend types in sync with backend
3. **Skipping deprecation:** Breaking changes need migration period
4. **Inconsistent naming:** Use same field names across stack

# React 19 Patterns in EZ Platform

Patterns and best practices for React 19 development in EZ Platform.

## Overview

EZ Platform uses React 19.0.0 with:
- Vite 5.4 for build tooling
- Ant Design 5.x for UI components
- React Query (TanStack Query) for server state
- i18next for internationalization

## Core Patterns

### 1. Lazy Loading with Suspense

Route-level code splitting for better initial load:

```tsx
// src/Frontend/src/App.tsx
import { Suspense, lazy } from 'react';

const DataSourcesPage = lazy(() => import('./pages/DataSourcesPage'));
const SchemaEditorPage = lazy(() => import('./pages/schema/SchemaEditorPage'));

function App() {
  return (
    <Suspense fallback={<LoadingSpinner />}>
      <Routes>
        <Route path="/datasources" element={<DataSourcesPage />} />
        <Route path="/schema/edit/:id" element={<SchemaEditorPage />} />
      </Routes>
    </Suspense>
  );
}
```

**When to use:**
- Page-level components
- Heavy components (charts, editors)
- Routes that aren't always accessed

**When NOT to use:**
- Small components
- Components needed immediately
- Components in render loops

### 2. useTranslation Hook Pattern

i18next integration for Hebrew/English support:

```tsx
import { useTranslation } from 'react-i18next';

const MyComponent: React.FC = () => {
  const { t, i18n } = useTranslation();
  const isRTL = i18n.language === 'he';

  return (
    <div>
      <h1>{t('page.title')}</h1>
      <p>{t('page.description')}</p>
    </div>
  );
};
```

**Translation key conventions:**
- `page.title` - Page-level titles
- `form.field.name` - Form field labels
- `button.save` - Button labels
- `error.required` - Error messages

### 3. Form State with Ant Design

Form handling with Ant Design Form component:

```tsx
import { Form, Input, Button } from 'antd';
import { useTranslation } from 'react-i18next';

interface FormValues {
  name: string;
  description?: string;
}

const DataSourceForm: React.FC<{ onSubmit: (values: FormValues) => void }> = ({ onSubmit }) => {
  const [form] = Form.useForm<FormValues>();
  const { t } = useTranslation();

  return (
    <Form form={form} onFinish={onSubmit} layout="vertical">
      <Form.Item
        name="name"
        label={t('datasources.fields.name')}
        rules={[{ required: true, message: t('errors.required') }]}
      >
        <Input />
      </Form.Item>
      <Button type="primary" htmlType="submit">
        {t('button.save')}
      </Button>
    </Form>
  );
};
```

### 4. Server State with React Query

Data fetching and caching:

```tsx
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { dataSourcesApi } from '../services/datasources-api-client';

const useDataSources = () => {
  return useQuery({
    queryKey: ['datasources'],
    queryFn: dataSourcesApi.getAll,
  });
};

const useCreateDataSource = () => {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: dataSourcesApi.create,
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['datasources'] });
    },
  });
};
```

### 5. RTL Layout Pattern

Handling RTL/Hebrew layouts:

```tsx
import { ConfigProvider } from 'antd';
import { useTranslation } from 'react-i18next';

const App: React.FC = () => {
  const { i18n } = useTranslation();
  const isRTL = i18n.language === 'he';

  // Set document direction
  useEffect(() => {
    document.documentElement.dir = isRTL ? 'rtl' : 'ltr';
    document.documentElement.lang = i18n.language;
  }, [isRTL, i18n.language]);

  return (
    <ConfigProvider direction={isRTL ? 'rtl' : 'ltr'}>
      {/* App content */}
    </ConfigProvider>
  );
};
```

**Technical fields (always LTR):**
```tsx
// Use .ltr-field class for technical content
<Input className="ltr-field" placeholder="192.168.1.1" />
<Input className="ltr-field" placeholder="/data/input" />
<Input className="ltr-field" placeholder="^[a-z]+$" />
```

## React 19 Specific Features

### Actions (New in React 19)

For form submissions with pending state:

```tsx
import { useActionState } from 'react';

const [state, submitAction, isPending] = useActionState(
  async (previousState, formData) => {
    const response = await saveDataSource(formData);
    return response;
  },
  null
);
```

**Note:** EZ Platform currently uses React Query for mutations.
useActionState is available for simpler form scenarios.

### use() Hook (New in React 19)

Reading promises in render:

```tsx
import { use, Suspense } from 'react';

function DataSourceDetails({ dataPromise }) {
  const data = use(dataPromise);
  return <div>{data.name}</div>;
}
```

**Note:** React Query remains preferred for data fetching due to
caching and invalidation features.

## Anti-Patterns to Avoid

### 1. Direct document.dir Manipulation
```tsx
// BAD: Direct manipulation
document.dir = 'rtl';

// GOOD: Use effect with language state
useEffect(() => {
  document.documentElement.dir = isRTL ? 'rtl' : 'ltr';
}, [isRTL]);
```

### 2. Hardcoded Hebrew Strings
```tsx
// BAD: Hardcoded text
<Button>שמור</Button>

// GOOD: Translation key
<Button>{t('button.save')}</Button>
```

### 3. Fetching in useEffect
```tsx
// BAD: Manual fetch in useEffect
useEffect(() => {
  fetch('/api/datasources').then(...);
}, []);

// GOOD: React Query
const { data } = useQuery({
  queryKey: ['datasources'],
  queryFn: dataSourcesApi.getAll,
});
```

        ├── he.json       # Hebrew translations
        └── en.json       # English translations
```
